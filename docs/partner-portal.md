# Carrier and customer partner portal

[Multi-stop routes](multi-stop.md) publish the complete frozen carrier route and exact rate document. The carrier accepts that full agreement and confirms intermediate service through its current offer after pickup, in route order. The portal displays each stop's completion/time; operations-only findings remain private, and the carrier retains its own submitted history. Native final delivery requires every intermediate confirmation. Historical offers retain their original route without exposing a replacement assignment.

Open **`/portal`** for counterparty-scoped access. Staff continue to use `/`. Carrier and customer identities never receive the tenant-wide staff workspace. The API constructs explicit partner projections; it does not send the staff aggregate and hide fields in the browser.

| Partner | Read access | Actions |
| --- | --- | --- |
| Carrier | Explicitly published offers, exact carrier confirmations, current shipment status/location for its active tender, retained own historical offers/decisions/submissions, original own POD downloads, explicitly shared files and release requests | Accept or decline the exact published revision; report physical pickup/location/delivery; submit POD for finance review; release or retain its exact published pre-pickup assignment |
| Customer | Its shipments, issued invoices, explicitly published quote revisions, original own quote/invoice downloads, explicitly shared files, scoped source status, and own native decision history | Accept/decline/withdraw an unbooked published quote; verify its canonical source; read/download |

Carrier views exclude customer identities/sell prices, margins, private procurement/review notes, unissued or unpublished carrier revisions, raw commerce orders, bank data, and other carriers' later assignments. Retired offers show their frozen own plan and rate, with no live location or new load version. Customer views exclude buy costs, carrier financial records, staff audit/queues, raw source payloads, and draft invoices. Partner access does not include generic shipment-file downloads; a financial agreement file cannot accidentally become a public POD merely because it belongs to the same load.

## Configure access

Use actual existing Freight carrier/customer IDs and independent credentials per person, or explicit Clerk organization grants. Configuration binds tenant, subject, role, and counterparty; none can come from browser headers, claims, query parameters, or request bodies. Carrier/customer IDs require 1–100 ASCII letters/digits/hyphens/underscores. Unknown/missing scopes fail startup. Staff roles must omit `counterparty_id`.

Credential-mode example, using the existing encrypted, eight-hour, HttpOnly, SameSite=Strict session mechanism:

```dotenv
FREIGHT_API_KEYS_JSON='{"replace-with-a-random-carrier-token-of-at-least-32-characters":{"tenant_id":"your-tenant","subject":"carrier:dispatcher-1","role":"carrier","counterparty_id":"your_existing_carrier_id"},"replace-with-a-random-customer-token-of-at-least-32-characters":{"tenant_id":"your-tenant","subject":"customer:transport-1","role":"customer","counterparty_id":"your_existing_customer_id"}}'
```

Do not give partners staff/service credentials. `/api/portal-session` verifies the partner API before creating its cookie. `/api/session` remains the staff sign-in endpoint; a partner credential cannot open the staff workspace. Sign-out clears the credential session. Revoking a configured static credential requires changing the deployment's credential configuration and restarting its API; it is not a self-service invitation lifecycle.

For the same StateSet Clerk instance described in [SSO setup](sso.md), configure separate explicit partner organization grants:

```json
{
  "org_actual_carrier_org": {
    "tenant_id": "your-tenant",
    "counterparty_id": "your_existing_carrier_id",
    "roles": {"org:freight_carrier_dispatcher": "carrier"}
  },
  "org_actual_customer_org": {
    "tenant_id": "your-tenant",
    "counterparty_id": "your_existing_customer_id",
    "roles": {"org:freight_customer": "customer"}
  }
}
```

Add these to API `FREIGHT_CLERK_JSON.organizations`, alongside separately configured staff organizations. A scoped partner organization cannot mix staff/carrier/customer roles. Only explicitly mapped live member roles gain access; unmapped roles fail closed. The API validates signed sessions and live membership/revocation on every request, including downloads and idempotency replay. Organization-bound gateway requests cannot reuse another signed organization or fall back to a credential cookie. The shared React SDK wrapper redirects partner sign-in/organization selection to `/portal`. Invitations, real organization membership, redirect/domain/MFA policy, and partner enrollment remain deployment-owned; no real account was created by this implementation.

## Publish and respond to a carrier offer

1. Tender the shipment and issue its current [carrier rate confirmation](carrier-rate-confirmations.md). Resolve proposed carrier charges, source review, release/custody holds, and current equipment/insurance qualification first.
2. Open the issued confirmation in shipment details. Select **Publish to carrier portal**, review its effect, then **Publish carrier offer**. This publishes the exact tender and rate document/hash to that carrier's configured users. It does not send email, accept the load, or start EDI transmission.
3. Publication counts as communicating the offer, even if the EDI outbox has zero attempts or nobody has yet recorded viewing it. Local proven-unsent withdrawal is unavailable thereafter. Use actual carrier release or the carrier's native decline. A fresh document or retry cannot erase a prior publication.
4. The carrier signs into `/portal`, inspects the frozen rate/terms/stops and exact download, then selects **Accept carrier offer** or **Decline carrier offer**. Acceptance requires explicit acknowledgement of that exact rate/revision, plus a response reference and note. The server binds the carrier account and authenticated subject to the decision; it does not accept caller-supplied prices, carrier IDs, statuses, or actors.
5. Acceptance requires the current tender/load version, current published rate/hash/basis, current equipment/insurance qualification, no coordination/proposed-charge hold, and fresh canonical Sync verification for imports. A source outage/change cannot become a new acceptance. Decline remains possible against the actual outstanding published offer during source cancellation/outage; it does not fetch or rewrite commerce data.
6. Accepted state is a genuine authenticated carrier decision and retains its publication, tender, exact rate/hash, reference, note, actor, and server time. It does not dispatch freight, create POD, approve invoices, post a journal, or execute a payment. A matching later 990 can confirm acceptance without duplicating the native decision. Decline retires only that tender and suppresses its pending jobs; a later carrier cannot inherit its old responses or public view.

A newly issued revision is private until separately published. Publishing a replacement requires the latest preceding publication ID; original publications/documents remain. A stale, superseded, retired, wrong-carrier, or changed-basis acceptance fails. Only outstanding tenders can receive native accept/decline; changes after acceptance use the existing operational coordination/release workflow. Historical published carrier documents stay downloadable by that carrier; unpublished newer revisions stay inaccessible.

## Respond to an exact carrier release request

Operations can explicitly publish a pending pre-pickup release request with a carrier message, frozen tender/disposition, and response/application deadline. **Carrier release requests** shows only publications for the authenticated carrier. Download the exact document, then **Confirm carrier release** with actual contact/reference/findings and an explicit no-pickup/no-custody acknowledgement, or **Retain assignment**. The latter preserves the assignment without accepting a tender or claiming pickup. A release requires the current version/hash and unexpired deadline; retention can close an expired request.

Publication retains ownership. A positive response applies immediately only if current custody, finance, and live handoff checks allow it. Otherwise the portal clearly reports an acknowledgement awaiting operations, while the carrier remains assigned. Staff must resolve the holds and separately apply the original evidence before the same deadline. The carrier's original actor, time, and proof hash remain separate from the later application. A new publication requires a fresh response. Pickup, superseded publications, other counterparties, and replacement tenders cannot use an old confirmation. Native release/retention does not depend on commerce source availability and does not agree a fee, approve an invoice, or execute payment.

Historical documents and own decisions remain; private operations reasons, hold details, staff application subjects, new carrier execution, and prices are excluded. The exact API shapes and tested competing pickup/release behavior are documented in [carrier release](tenders.md#authenticated-carrier-release) and the [API](api.md). Existing staff attestations remain available for actual correspondence outside the portal.

## Publish customer quotes and record decisions

1. Staff issues the customer quote with an actual selected carrier offer, valid capacity, and configured issuer. In **Quotes**, open the issued quote and choose **Publish to customer portal**. Review the exact revision/customer/price, acknowledge publication, and save. Only issued, unexpired eligible revisions may be published. Publication freezes the customer plan, inclusive sell amount, terms, deadline, issuer identity, original HTML bytes/hash, and preceding publication link. It advances the quote version without accepting, booking, tendering, or sending an external message.
2. The configured customer opens `/portal` and reads **Your quotes and amendments**. Only explicitly published revisions for its counterparty are present. Inspect the frozen plan and **Download published quote**, then choose **Accept customer quote**, **Decline customer quote**, or **Withdraw quote or acceptance**. Acceptance requires acknowledgement of that exact document/plan/price/terms, an actual customer contact, a decision reference, and findings. The API binds the authenticated subject and counterparty; caller-supplied identities, prices, or staff powers are rejected.
3. For an imported shipment, **Verify commerce order** fetches the canonical order using the configured Sync tenant credential and shows only order identity/number, status, verification time/availability, and the digest used internally to bind consent. Acceptance fetches and fences a fresh check again. An imported amendment against cancelled, returned, or unknown source state needs deliberate authorization of the published amended transportation plan despite that status. A changed canonical digest rejects stale consent. No raw order, metadata, internal tags, line pricing, upstream error, or staff source-review note is exposed. This authorizes the transportation plan; it does not change or attest unseen commerce contents.
4. Acceptance retains the publication, exact document hash/revision, contact/reference/note, authenticated actor, server time, and applicable scoped source consent. Decision history shows the source status and verification time at acceptance separately from the latest commerce status. Staff then books or activates separately, rechecking deadlines, selected carrier, source, custody, original agreement, and financial prerequisites. An amendment acceptance leaves the existing agreement and shipment unchanged until activation. Native decline/withdrawal remains available against the current unbooked revision without upstream IO, including during source outage or cancellation. A booked shipment requires operational coordination; customers cannot cancel it or release carriers through this quote decision.
5. Revision, withdrawal, expiry, and replaced capacity cannot reuse old acceptance. New revisions remain private until explicitly published. Prior customers keep their original frozen documents and own decisions but cannot see a replacement customer's revision, live version, source, or subsequent decisions. Published HTML remains unchanged after acceptance/booking; the portal separately marks its current/historical agreement status. Corrupt document bytes or snapshot hashes fail closed. Native business-command replay binds the authenticated customer and original exact request; another person's guessed key cannot retrieve its response.

Customer quote routes use the **publication ID** in portal URLs:

- Staff `POST /v1/quotes/{quote_id}/portal-publications`: `{expected_version, expected_previous_id?}` under `operations.write`.
- Customer `POST /v1/portal/customer-quotes/{publication_id}/response`: `{expected_version, revision, document_sha256, decision: "accept"|"decline"|"withdraw", contact, reference, note, source_digest?, authorize_transport?}` under `portal.customer.quote.respond`. Source fields apply only to acceptance of an imported amendment; contact/reference/note require 1–200 characters.
- Customer `POST /v1/portal/customer-quotes/{publication_id}/source/refresh`: `{}` and an `Idempotency-Key`. This verification always fetches current canonical data rather than replaying a potentially stale observation; its response is a scoped quote view. It does not change the quote or create customer consent.
- Customer `GET /v1/portal/customer-quotes/{publication_id}/statement`: exact original bytes, SHA-256, attachment/no-store protections. Carrier, another customer, drafts, and unpublished revisions cannot access it.

All customer commands enforce live scope before replay and source IO. Quote/publication versions and source grants are checked again inside the tenant transaction. Staff workspace history includes publications without HTML plus native decision records; partner responses contain no private quote aggregate or procurement records. Existing staff recording of genuine external customer correspondence remains supported and separately attributed.

## API and persistence

- `GET /v1/portal`: only `carrier`/`customer` roles. Returns server-scoped `kind`, `name`, access information, and carrier `offers`/`release_requests` or customer `shipments`/`bills`/`quotes`, plus explicitly scoped `files`. No staff directories, original source orders, private records, tokens, or idempotency receipts are returned.
- `POST /v1/loads/{id}/portal-offers`: staff `operations.write`; `{expected_load_version, rate_confirmation_id, expected_previous_id?}`. Commits a publication and advances the load version.
- `POST /v1/portal/offers/{id}/response`: `portal.carrier.respond`; `{expected_load_version, decision: "accept"|"decline", rate_confirmation_id, rate_sha256, reference, note}`. Reference/note require 1–200 characters. Role, tenant, carrier, and subject are server-owned.
- `POST /v1/portal/offers/{id}/tracking`: `portal.carrier.report`; `{expected_load_version, kind: "pickup"|"location"|"delivery", observed_at, location, reference, note}`. Observation timestamps require RFC3339 with an explicit offset; future times fail. Text fields require 1–200 characters. The portal's time field is explicitly UTC.
- `POST /v1/portal/offers/{id}/pod?expected_load_version=...&filename=...&reference=...&note=...`: `portal.carrier.report`; raw PDF/JPEG/PNG bytes with their actual media type, maximum 10 MiB. Query fields are strict; callers cannot choose document kind, carrier, tender, subject, review status, or financial state.
- `GET /v1/portal/submissions/{id}/content`: only the carrier that submitted that POD, with exact bytes, attachment headers, no-store, and SHA-256 verification. Tracking-only submissions and other counterparties return 404. Generic staff file IDs cannot be used here.
- `GET /v1/portal/rate-confirmations/{id}/statement`: only the carrier whose explicit publication owns that document; exact original bytes/hash.
- `GET /v1/portal/bills/{id}/statement`: only that customer, after issuance; void history remains marked and available. Other parties and drafts return 404.

All writes require `Idempotency-Key`. Current identity and resource ownership are checked before replay. Internal fingerprints include the verified counterparty and subject; another partner cannot retrieve a response under a guessed/shared key. Business changes, native decision, audit, and receipt commit in the existing tenant transaction. Approved carrier-charge evidence is byte-checked before publication/acceptance. Corrupt rate bytes or supporting files roll back publication/response, versions, audit, and receipts together.

Migration `010_partner_portal.sql` introduced publications in format 8; `011_carrier_submissions.sql` introduced native tracking/POD evidence in format 9; `012_customer_quote_portal.sql` introduced immutable customer publications and native decisions in format 10; `013_document_sharing.sql` introduced scoped original-file grants, revocations, and download authorizations in format 11; `014_carrier_release_portal.sql` advances it to **12** for immutable carrier release requests, native responses, and original carrier evidence with separate application; format **13** added the private staff carrier contract catalogue and procurement source revisions; format **14** added full multi-stop plans, actual intermediate service, and retained correction chains; format **15** fences obsolete execution/Sync behavior; current format **16** retains reviewed native movement time corrections and effective actual-time chronology/writeback. The [shared execution timeline](execution-timeline.md) exposes operational kinds/times to both scoped partner roles while keeping staff evidence references/actors private. [Reviewed native movement corrections](movement-corrections.md) additionally show effective/original times and a correction marker without staff contact, reference, findings, or actor; the carrier’s own report remains unchanged. These preserve business fields, files, and original migration history. The format fence prevents an older API from discarding partner evidence or ignoring its custody effects. See [deployment/rollback](storage.md).

## Report movement and submit POD

On an accepted current published assignment, select **Report shipment progress**. Report actual pickup first, then in-transit locations or delivery, using the actual observation time, location, and supporting reference/note. Each report binds the authenticated subject, carrier, publication, and exact tender. Unknown fields, wrong counterparties, unaccepted/retired tenders, superseded publications, future timestamps, and stale load versions fail before mutation. Another person's guessed idempotency key cannot retrieve a response.

Native movement shares the established carrier-status progression and tracking watermark with EDI. Earlier location observations remain in your submission history as ignored for current progress; they do not overwrite a later location. Delayed physical progression retains the higher watermark. Pickup blocks a pending carrier release; reporting it does not invent an internal driver/equipment assignment. A commerce source hold cannot erase actual physical evidence: movement remains local, and the Sync worker independently holds unsafe writeback instead of shipping a cancelled order. A native report is carrier evidence, not an automatically generated EDI document or proof of external transport delivery.

After delivery, select **Submit POD** and upload the actual receiver file. File bytes, SHA-256 metadata, carrier provenance, attachment, shipment version, audit, Sync outbox, and idempotency receipt commit together. The original bytes are immutable and immediately available to staff reviewers and the submitting carrier. Submission remains unreviewed and cannot approve an invoice, issue customer billing, or execute payment. Finance uses the existing document review controls. Delivery without a file does not establish proof.

A carrier cannot replace pending, accepted, or financially locked proof. After finance rejects the attached evidence, the carrier may submit a replacement; the rejected original remains downloadable in its own history. Staff review notes stay private; the carrier sees only the review status. Self-service history never grants access to other staff documents, customer financial evidence, another carrier's submissions, or a replacement carrier's execution. No POD is automatically shared with the customer portal.

## Shared shipment files

Staff can explicitly share a stored file with your customer account or a specific carrier tender. **Shared shipment files** shows only grants for your verified role/counterparty, with the original file description, recipient message, review state, and exact download. Staff content-review/revocation notes and other recipients remain private. Staff content-sharing review is separate from finance evidence review; sharing does not approve billing, attest a signature, or communicate carrier acceptance.

A revoked or rejected-file grant has no working download. Its original metadata remains in history, and already downloaded copies are not recalled. A new grant after revocation has a new URL. Earlier carrier/customer shares retain only their original file; they do not expose replacement-party execution or commercial data. A carrier's own submitted POD and published rate/quote/invoice downloads use independent controls.

File downloads verify current access and original bytes under the same transaction as the authorization audit. These records prove authorization to send bytes, not that the network completed delivery or that the partner read/accepted the file. Carrier file publication counts as communication of its selected tender, so revoking it cannot restore proven-unsent withdrawal. See [sharing workflow, permissions, revocation ordering, and API](documents.md#share-original-files-with-partners).

## Qualification and remaining work

Independent tests verify that the 125,001-cent carrier price is visible while the 150,001-cent customer price and private staff proof remain absent. Partners cannot reach staff routes, another counterparty's documents, a draft invoice, an unpublished revision, or a new carrier's execution after retirement. Forged headers/claims/body identities, stale versions, changed hashes, expired qualifications, repeated responses, and crossed organization bindings fail. Canonical Sync HTTP tests hold native acceptance after upstream cancellation while allowing an actual decline without unsafe writeback.

Reconnect preserves exact documents, native actor/proof, empty financial journals, and tenant isolation. The actual sibling EDI codec harness publishes/accepts the document accompanying a real 204, then applies a real parsed 990 without duplicating the native decision. Production browsers exercise staff publication, separate carrier/customer sessions, native mobile acceptance, scoped exact downloads, sign-out, cross-party denial, and live signed Clerk membership/revocation through the gateway. All records/providers are synthetic.

Native carrier qualification covers physical progression, current-tender ownership, stale reports, future/forged input denial, release-after-pickup protection, original file downloads, strict counterparty scopes, rejection/replacement history, private finance notes, and invoice approval remaining blocked until review. Self-service invitations and finer partner roles remain further workflows.
