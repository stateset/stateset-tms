## Write verification after traffic

The 2026-10-21 combined diagnostic withheld five of six writes because of the client, not the server. The one sent write returned in 4.19 seconds. The harness then held the write lane for 53.03 seconds while it fetched, decoded and compared the writer tenant's complete 28.8 MB original. That diagnostic stays failed, and its budgets are unchanged.

A plan can now declare `"write_verification": "post_traffic_chain"` in `sustained`. Omitting it keeps `per_write`, which is the earlier behaviour. In chained mode, each write sends `expected_version` from the previous write's own response. The write is trusted only when it returns a 200 whose load has exactly the next version and the commanded location, and is not a replay. A 503 is held as a claimed non-application. Any other status, transport error or mismatched response stops every later write, as before.

After traffic drains, the harness reads one complete writer original. It rebuilds each intermediate original from the response load and the final events and receipts, and passes every consecutive pair to the unchanged per-write classifier. The rebuilt final original must equal the observed one byte for byte. As a result, these each fail the run: a 503 that actually committed, a changed unrelated root or load, a response that differs from its receipt, and a missing receipt. Exact replays then use the verified receipts. The negative controls are in `scripts/test_financial_capacity.py`. A pass in chained mode still needs a fresh run on a quiet host before it can count as capacity evidence.
