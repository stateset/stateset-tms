# Commerce source changes and transport authorization

A commerce cancellation can arrive after a carrier has accepted freight or taken custody. Freight retains that physical and commercial history. A source change holds new transportation commitments until operations records the customer's actual decision against the current shipment plan; it never silently cancels the carrier, changes prices, reverses invoices, or removes documents.

## Canonical evidence and checks

The implementation follows the raw sibling Sync code: `src/domain/mod.rs` (`Order`, camel-case fields and snake-case status), `src/database/orders.rs` (`update_order_tracking`), and the canonical order/tracking HTTP handlers. The original import stays in `load.source_order`. `source_checks` stores the most recently verified raw order, SHA-256 business digest, identity, observation version, timestamps, source actor, and errors. `source_reviews` retains changed field names, previous authorized and new raw snapshots, the freight plan, superseded reviews, and named customer decisions. Unknown business fields participate in change detection.

Freight reads `GET /v1/tenants/{configured tenant}/orders/{original UUID}` with the server-owned API key before imported-load tendering/dispatch, quote booking, replacement procurement, carrier rate-confirmation issuance, carrier portal publication/native acceptance, and each outbound integration handoff. The request uses a five-second timeout, bounded two-megabyte response, no redirects, exact order identity, and an optional returned tenant check. Client bodies cannot supply a replacement snapshot. Network I/O happens outside the tenant transaction. The subsequent transaction fences the source observation version and a 30-second validity window, alongside normal business versions. A concurrent newer observation makes the old grant unusable. Failed actions retain their source observations/reviews, and do not consume the failed business request's idempotency key.

The worker also checks up to four active imports per configured tenant on a rotating schedule every fifteen worker ticks (nominally thirty seconds; upstream/queue processing adds time). This is polling, not an upstream push feed or a guaranteed maximum detection latency. Manual **Refresh commerce order** is available in shipment details; **Integrations → Commerce source exceptions** opens shipments needing review. Unresolved reviews remain visible after local completion/cancellation; expired checks alone do not put closed shipments back into this action queue. Older imports without a check require a successful refresh before a new commitment. Observation-only polling does not bump shipment versions unless the business meaning or authorized freight plan changes.

The digest ignores `updatedAt`, tracking/latest-movement telemetry, and integration attempt/error/sync timestamps. Pending and processing are equivalent for this guard; tags are compared as a set. Fulfillment state, item details, locations, source identifiers, and unknown fields remain significant. The full raw snapshot remains visible even for ignored telemetry. The Sync tracking endpoint itself sets status to `SHIPPED`: after a Freight tracking attempt, that shipped echo is treated as an expected effect, while fulfillment changes still require review. This is a known contract limitation: the source does not identify which writer caused a particular shipped transition.

## Review a change

1. Open the shipment's **Commerce order review**, refresh its canonical order, and compare previous/latest source evidence with the current freight plan. Source outages remain visible and block new commitments.
2. Obtain actual confirmation through your established customer channel. For an active/completed known source status, record **Customer confirms the current freight plan**. Cancelled, returned, and unknown source statuses require **Customer explicitly authorizes transport despite source status**. Record the actual contact, original confirmation reference, and findings. The API rejects stale review/load/digest versions; the last successful source check must be within five minutes.
3. To stop transport, use **Withdraw unsent tender** when provably untransmitted, or the existing externally confirmed carrier release process when handed off/accepted. Cancel the freight shipment through that safe workflow. Then select **Close review after safe shipment cancellation**. Closing a review cannot itself release a carrier or cancel a load.
4. If another business change arrives, the earlier decision remains recorded and a new review is required. A change followed by an upstream reversion also needs review; neither event silently clears a hold. Customer authorization is tied to the freight plan. Re-planning after authorization requires renewed review.

Only `operations.write` can refresh or resolve source reviews. All authorized staff readers can inspect the source evidence/history. Finance and integration-only credentials cannot assert customer transport consent. Existing document, carrier release, charge, bank, and financial approval policies continue to apply independently.

## Tracking and handoff behavior

Fresh verification happens before a queued 204 enters its transmission attempt. A held unattempted EDI tender keeps its original payload and `not_started` transmission proof. Local withdrawal also requires absence of a portal publication or recorded external carrier rate-confirmation handoff; an unsent EDI payload cannot erase a separate carrier communication. Other eligible loads can still hand off. Existing lease tokens and destination/load ordering continue to fence retries.

The sibling Sync `update_order_tracking` unconditionally sets the commerce order to `SHIPPED`. Freight therefore **holds tracking writeback** when the canonical source is cancelled, returned, fulfilled, delivered, or unknown, and when the Freight tracking payload represents cancellation even if the source is pending. Recorded customer transport consent does not override this restriction. These jobs retain their payload, reason, attempts, and audit evidence; retry fetches canonical state again and cannot bypass the guard. Operations must reconcile with commerce through its established order workflow. The TMS does not pretend that cancelling freight cancels the commerce order.

Pre-pickup payloads (`planned`, `tendered`, `accepted`, `dispatched`) are retained as **`local_only`**, including withdrawal/decline and gate observations before actual pickup. Sending them through the current tracking endpoint would prematurely mark the commerce order shipped. This is a terminal local retention decision for that payload, with its original body, attempts, transmission markers, and explanation preserved; transport Retry cannot force it upstream. It creates no successful upstream acknowledgement. Later actual pickup/delivery tracking can proceed past these retained facts in order. Existing prior transmission attempts remain recorded as such and are not undone or relabeled unattempted. Cancellation payloads and physical updates against unsafe canonical source statuses continue to use their existing `held` reconciliation behavior.

Carrier pickup/delivery/invoice evidence, local physical events, safe release/withdrawal/cancellation, and financial reconciliation remain available while source review is pending. A carrier can already hold the goods: suppressing physical truth or reversing its liability would make the workspace misleading. Ordinary active-order physical tracking continues through the existing Sync JSON tracking contract; a successful response does not claim that commerce's detailed fulfillment state matches the Freight lifecycle.

[Customer amendments](customer-amendments.md) capture fresh canonical source consent with the actual customer acceptance. Activation appends a linked source decision bound to the new plan, retains any superseded source review, and preserves the original merchant order. A changed business digest between acceptance and activation requires renewed acceptance.

## API

- `POST /v1/loads/{id}/source/refresh` accepts exactly `{}` and a new `Idempotency-Key`. Returns `{data: SourceCheck, replayed}`. A replay returns the original observation without another upstream request; fetch the workspace for current state. Role authorization applies before replay or upstream I/O.
- `POST /v1/source-reviews/{id}/resolve` requires `expected_load_version`, `expected_version` (review), `expected_digest`, `decision` (`confirm_plan`, `authorize_transport`, or `cancel_transport`), `contact`, `reference`, and `note`. Unknown fields are rejected; text evidence is required and bounded to 200 characters.
- Workspace adds `source_checks`, `source_reviews`, and per-load `source_control` with the check, hold/unavailable state, current commitment eligibility, and source-status writeback eligibility. Payload-specific cancellation checks additionally apply at handoff.
- Known review holds return 409; unavailable/expired source checks return 503. New canonical observations survive a rejected business action. No successful carrier/payment/commerce cancellation is fabricated.

## Limits and recovery

The canonical GET and subsequent remote write are separate requests. The current Sync API offers no conditional tracking update, order reservation, or shared transaction. These checks guarantee a fresh, version-fenced local decision; they cannot eliminate a commerce change between verification and transmission. Conditional mutations/reservation and a qualified upstream amendment/cancellation push feed require additional upstream contracts. Live partner/tenant commissioning remains separate from the owned fixture qualification.

A source outage preserves the last verified snapshot and review evidence, records the error, and blocks new commitments. Restore the configured connection and refresh. Do not change source IDs, edit raw JSON in the database, or reset queue attempt evidence to clear a hold. If canonical data regresses to an older `updatedAt`, drops a previously present revision timestamp, or returns an invalid timestamp, investigate replication/provider state and refresh from the authoritative source. Source versions fence concurrent observations regardless of timestamps.

Migration `006_source_reviews.sql` advances storage format 3 → 4 while preserving every prior field and file byte. Previous APIs are fenced so they cannot discard source reviews on aggregate rewrites. Follow the [storage deployment/restore procedure](storage.md).
