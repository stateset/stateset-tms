# Workspace access

[Encrypted browser recovery](sealed-save-journal.md) additionally verifies the complete owner before sealing or opening request contents. It derives tenant/subject from the actual API access response, requires staff workspace access, and binds organization and the API-validated signed Clerk session. A caller cannot select another operator’s scope or relabel a captured envelope to open it. Encryption does not grant permission to apply or stop the original business operation.

[Browser save restoration](browser-save-journal.md) opens only after API-verified tenant/subject access and scopes retained input to that operator, authentication mode, organization and Clerk session where applicable. Shared saves additionally bind the reviewed tenant/subject at the gateway using the same captured upstream identity as the forwarded POST. A changed credential cookie cannot redirect a retained body into another tenant. This display/replay guard supplements ordinary API authorization; local browser data is not an authorization boundary.

[Resolving an uncertain original save](save-resolution.md) requires `saves.recover` plus the original route’s capability. Operations, finance, integration and administrator roles receive `saves.recover`; viewer and partner roles do not. Resolution cannot grant authority to apply a business operation. The verified tenant/actor and canonical original path/body/key determine the receipt or stop; clients cannot override identity or choose an internal operation.

[Control tower](control-tower.md) reads use `workspace.read`. Named self-claim, notes, follow-up changes, bounded deferral, release, and explicit reconciliation require `operations.write`. Only administrators have `operations.configure` for tracking policy or may release another owner. Case requests bind the authenticated subject, reviewed source/active state, and case version before mutation; a client cannot assign another person or mark an active source condition resolved. Partner roles cannot read cases, private notes, owners, policy, or metrics.

[Native movement time corrections](movement-corrections.md) require `operations.write`. Carrier, customer, viewer, finance-only, and integration roles cannot correct a carrier report. Staff readers can inspect the original source and correction evidence; scoped partner timelines expose only original/effective times and a correction marker. Named review, exact source/predecessor, current load version, chronology, and financial locks are enforced server-side.

[Intermediate stop service](multi-stop.md) requires `operations.write` for staff recording/corrections or `portal.carrier.report` for the current assigned carrier's own publication. Customer, viewer, finance-only, and integration roles cannot assert service. The server derives tender, actor, recording time, and evidence digest; staff corrections retain the entire original chain.

The API authorizes every protected endpoint using its registered route, before reading request bodies, replaying idempotency receipts, or contacting business upstream services. Staff identity verification consults Clerk before granting that business access. New routes remain denied until explicitly assigned a capability. Browser controls reflect the same capability list returned by the API; changing the operations perspective never changes access.

Staff can use the existing StateSet Clerk instance through [the implemented SSO workflow](sso.md). The API validates signed sessions, reads live membership/status, and maps explicitly approved organizations/roles to existing tenants. Browser claims and public organization metadata cannot grant a tenant or role. Static credentials below remain supported for explicit service access and credential-mode deployments.

[Carrier rate confirmations](carrier-rate-confirmations.md) require `operations.write` for issuance, actual external handoff attestation, erroneous-evidence retraction, and coordination resolution. All tenant staff readers may inspect/download the retained document and evidence. Prices, carrier, issuer, HTML/hash, and actor derive server-side. An external handoff cannot be recorded by finance/integration/viewer roles; recording it is separate from carrier acceptance or any automatic delivery.

[Cancellation fees](cancellations.md) use `charges.write` for proposals and `finance.write` for approval/rejection/reversal. All staff readers can inspect their retained agreement/decision history. Integration credentials cannot assert human carrier release or fee confirmation. Existing finance permissions govern separate invoice, bank, refund, and credit-application targets.

[Quoting and carrier procurement](quotes.md) require `operations.write` for drafts/revisions, actual offer/decision evidence, booking, reconfirmation, and replacement procurement. All staff readers can inspect/download quotes. Viewer, finance-only, and integration roles cannot assert a customer agreement or purchase rate. Quote/load versions and existing-source plan/ownership checks apply before mutation; organization-bound requests/downloads use the same gateway identity controls.

[Carrier lane agreements](carrier-contracts.md) use `operations.write` for recording/revising/withdrawing reviewed external terms and confirming capacity at a sourced rate. Every tenant staff reader can evaluate and inspect/download the private catalogue. Carrier/customer portal roles cannot use these staff routes or receive private contract terms/evidence. The server derives the exact rate/carrier/source revision, verifies the original hashes and reviewed versions, and retains the authenticated capacity confirmer separately from the agreement's original source actor. Imported replacement procurement uses the existing fresh canonical Sync check and transaction-fenced source grant.

[Commerce source review](source.md) requires `operations.write` for refresh and recorded customer transport decisions. All staff readers can inspect original/latest order evidence and review history. Finance-only and integration-only roles cannot authorize transport against a source change.

[Customer amendments](customer-amendments.md) also require `operations.write` for proposals, customer/source consent, and activation. All staff readers can inspect the original/successor agreements; historic superseded agreements cannot be revived by reconfirmation or replacement procurement.

Configure separate random credentials for people and services:

```dotenv
FREIGHT_API_KEYS_JSON='{"replace-with-a-unique-random-operations-token":{"tenant_id":"your-tenant","subject":"user:dispatcher-1","role":"operations"},"replace-with-a-unique-random-finance-token":{"tenant_id":"your-tenant","subject":"user:accountant-1","role":"finance"}}'
```

Tokens must have 32–512 printable ASCII characters without whitespace. Tenant IDs contain 1–100 ASCII letters, digits, hyphens, underscores, or periods. Scoped entries require a nonempty subject (at most 100 characters) and an explicit recognized role. Unknown fields, misspelled roles, and missing roles fail startup. Configuration errors do not print credential values.

Use separate `carrier`/`customer` identities with required server-owned `counterparty_id` for the [partner portal](partner-portal.md). Those roles cannot read the tenant workspace or staff routes. Carrier access is limited to explicitly published offers/documents for that carrier and native responses to current offers, current-assignment physical tracking/POD submission under `portal.carrier.report`, and exact downloads of its own submitted files; customer access includes its shipments, issued invoices, and explicitly published quote revisions/documents. Only the customer role has `portal.customer.quote.respond` for native decisions and scoped canonical source verification. Customer acceptance cannot book/activate transport or mutate procurement; those remain operations actions. Staff roles cannot select a counterparty to enter the portal. Reading upstream order candidates requires operations permission. Integration retry can apply authenticated carrier invoice evidence, but cannot approve invoices or prepare settlements. Signed EDI webhooks use their independent versioned HMAC credentials and are not bearer endpoints.

Tender withdrawal, carrier release requests/confirmation/retention, and carrier conflict resolution require `operations.write` (`operations` or `admin`). These actions record the authenticated subject and require the current load version. Integration credentials may submit signed carrier evidence but cannot confirm a human carrier release or resolve custody conflicts. Finance approval is blocked by unresolved tender incidents.

Operations also publishes exact [carrier release requests](tenders.md#authenticated-carrier-release) and applies retained native acknowledgements under `operations.write`. Only scoped carrier identities have `portal.carrier.release` to answer their own current published request; this grants no staff release or custody-resolution powers. Native evidence keeps the original carrier subject/time/contact/hash even when operations applies it later, with a separately recorded application actor/time. Pickup, financial, deadline, and live handoff checks still govern application. Carrier downloads use `portal.read` and expose only that carrier's published release documents. Finance-only, integration, viewer, and customer roles cannot publish, apply, or impersonate a native carrier response.

Appointment booking/rescheduling/cancellation and gate evidence/corrections also require `operations.write`, load-version checks, and server-recorded subjects. Readers can inspect the original appointment and gate history. An integration credential cannot assert a human facility confirmation or edit gate evidence through these routes. Gate times do not create finance approval or charges.

`operations`, `finance`, and `admin` additionally receive `documents.write` to upload immutable shipment files. Every tenant role can download its tenant's files. Document and external POD reviews require `finance.write`; changing a POD attachment requires `operations.write`. Uploading or reviewing a file does not grant the other role's capabilities. Invoice approval and settlement require accepted delivery evidence and verify stored byte integrity before committing.

Customer invoice creation/revision/issuance/voiding, supplemental customer billing and explicit corrections, credits (including paid-customer credits with actual confirmation), billing issuer configuration, and bank reconciliation/reversal including customer refunds require `finance.write`. Tenant roles can read invoice statements and the freight journal export. The API fixes identity before idempotency lookup and applies the same tenant boundary to these records. No role here initiates bank transfers.

`operations`, `finance`, and `admin` receive `charges.write` to propose documented additions or explicit corrections. Approving/rejecting/voiding charge decisions requires `finance.write`. Operations cannot approve its proposal through a different perspective, forged actor field, or replay. Every mutation checks current load/charge versions and records the server-authenticated subject. A named finance decision verifies the counterparty agreement; it does not automatically send that agreement, approve POD, or execute a payment.

Carrier financial adjustment creation/approval/rejection/reversal, canonical invoice classification/dismissal, and carrier-refund bank reconciliation require `finance.write`. Signed EDI/integration credentials can retain an additional document but cannot classify it or post a payable. Every tenant role can inspect its tenant's retained financial evidence. Counterparty confirmation and posting/reversal actors are recorded separately; the original decision is preserved.

Carrier credit applications, reversals, and explicit corrections also require `finance.write`. Operations/integration credentials cannot reallocate financial credits. Every tenant role may inspect the confirmation and source/target history; the browser hides writes through disabled controls and the API independently denies them. The caller cannot supply the carrier, currency, status, or recorded subject. Source/target settlement versions protect against competing allocations, payouts, and refunds.

Audit events store the verified subject. In credential mode, rotate a person's credential without changing its configured subject to preserve attribution; the browser stores that credential in an encrypted cookie. Configuration changes require restarting every API replica, and old cookies cannot bypass them. In Clerk mode, the immutable Clerk user ID supplies the subject; membership/role/session changes apply to subsequent requests through live verification. The SDK uses its short-lived session cookie/token design and Clerk sign-out rather than the eight-hour credential cookie. Do not share identities if individual accountability matters.

Legacy entries such as `"token":"tenant-id"` retain administrator access and use a one-way credential fingerprint as their audit subject. Migrate these to explicit subject/role objects before issuing limited access. Demo access is also an administrator of synthetic demo data.

Static grants and Clerk-backed dynamic staff memberships are enforced. Clerk instance/domain/role enrollment and live SSO commissioning remain deployment work. Counterparty filtering is enforced in the partner portal. Partner enrollment/invitations, finer partner/facility scopes, and enforced separation between invoice entry and approval remain additional identity/policy work. Finance approval still requires the existing business checks for matched amounts, delivery, and POD evidence.

[Partner file sharing](documents.md#share-original-files-with-partners) uses `documents.write` for operations/finance/admin publication and revocation. Carrier invoice/rate files additionally require finance/admin for creation and cannot target customers. The server owns the recipient/tender/actor/role and checks original bytes transactionally. Partner downloads under `portal.read` are limited to that role/counterparty's exact grants; they check revocation and bytes and commit an authorization audit under the same tenant lock. Staff readers retain their existing generic file access. Content review and revocation reasons remain private; downloaded copies and independent published documents are unaffected by revoking a grant.

## Dialog background isolation

The shared staff and partner dialog keeps the active task available while making background sibling subtrees inert and hidden from accessibility queries. It follows the dialog’s ancestor path, so dialogs embedded in shipment details and dialogs rendered through a portal use the same boundary. A nested dialog owns interaction until it closes; its parent temporarily reports `aria-modal="false"`, then regains its original modal state. Existing Tab, Shift+Tab, Escape, focus restoration and page-scroll behavior remain covered by the browser suite.

The boundary observes newly mounted background controls and restores the exact prior `inert`, `aria-hidden` and parent `aria-modal` attributes on close or unmount. Previously hidden controls stay hidden; an original `aria-hidden="false"` value is preserved. Native inert prevents background programmatic focus as well as ordinary interaction. Server-side tenant and role checks continue to decide who may submit each operation.

Two actual preceding-production Chromium cases reproduce background focus and accessibility exposure at 1280- and 390-pixel widths. Both pass on the new build. A third case opens a real nested carrier-confirmation form, verifies parent isolation and focus restoration, mounts a late background control, restores preexisting attributes and confirms that cancellation neither issues a carrier document nor changes the load version. All 108 production-browser cases pass against the new image’s exact compiled application and traced dependencies, under the restricted PostgreSQL verification-only login.

The first full attempt remains failed: 95 cases passed, six failed and seven did not run. Five cases used accessibility-filtered queries to inspect background data during a dialog; six selectors now explicitly include hidden background nodes while retaining every content, version, original-request, overload and replay assertion. The other failure was an isolated fixture’s missing historical qualification receipts; exact original receipts were copied and their existing hash checks retained. The full subsequent suite has zero skips, failures or retries. The earlier missing relative-identity fixture and incorrect exact navigation-title selector are also retained as failed attempts.

Existing preview processes on ports 36445/36446 continue to use their preceding compiled artifact. The qualified new web image and application tree are recorded in the integration receipt for a separate deployment. These synthetic Chromium checks improve a specific interaction boundary; independent keyboard/screen-reader trials, measured operator task completion and onboarding/support outcomes still require operating evidence.
