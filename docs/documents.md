# Shipment documents and delivery evidence

Carriers can submit original receiver POD through the [scoped partner portal](partner-portal.md#report-movement-and-submit-pod) after delivery. That path atomically stores and attaches the file with authenticated carrier/tender provenance and an unreviewed status. Carrier submission grants neither finance review nor generic staff-file access. Rejected originals remain retained when a replacement is submitted.

Open a shipment and use Shipment documents to retain a PDF, JPEG, or PNG. Supported kinds are POD, bill of lading, rate confirmation, carrier invoice, and other. Files may contain up to 10 MiB. Filenames, declared media type, and basic format signatures must agree. The application stores the original bytes unchanged and computes their SHA-256 digest. These checks identify and preserve the file; they do not establish signature authenticity.

In real workspaces, `freight_document_content` stores bytes in PostgreSQL, separately from workspace JSON. An upload commits its bytes, metadata, audit entry, and idempotency receipt in the same transaction. Repeating the same upload key returns the original document. A changed filename, kind, media type, or content under that key conflicts. Concurrent requests from different API replicas cannot create duplicate files under one key. Demo bytes live in memory and reset with the API, just like demo records.

All tenant staff roles can download documents belonging to their tenant. Downloads check the stored byte length and digest, return attachments with `nosniff`, and disable caching. File names support Unicode. Foreign tenant IDs return 404 even when the caller knows the document ID. Workspace responses include metadata and review history, never file bytes. Both the web gateway and API bound upload sizes before retaining the full body.

Operations and finance can upload files. Only finance/admin can review them. Reviews require an explicit accepted/rejected decision, a note, and the expected document version. The server records the authenticated subject and timestamp. Review history is append-only; stale concurrent decisions conflict. Files cannot be overwritten or deleted through the API. Upload a new document when a carrier supplies replacement evidence.

For a stored POD, select the document when confirming delivery, or choose Use as POD after a 214 has confirmed delivery. The file must belong to that load, have kind `pod`, and not be rejected. It may await finance review; the shipment remains delivered while invoice approval stays blocked. A D1 alone still supplies no POD.

For evidence held externally, enter the actual reference and have finance use Review external POD. Finance must inspect that external evidence and record the review; the application does not fetch arbitrary external URLs. Reviews bind to the exact reference. Replacing it clears the current review and requires a new decision. Earlier decisions remain in the shipment audit.

Carrier invoice approval, customer invoice issuance, and settlement preparation require delivered status and accepted evidence; carrier approval also requires matched amounts. For a stored POD, each new approval/issuance/settlement also checks the original bytes inside the database transaction. Missing or altered bytes abort the entire mutation, including audit, journal, and idempotency writes. Restoring the original bytes allows the original failed request key to succeed. Once customer billing is issued, a carrier invoice approved, or a settlement prepared, its POD cannot be replaced or rejected. A later dispute requires an explicit finance reconciliation workflow; it cannot silently invalidate previously approved evidence.

Existing external references load without automatic acceptance. Previously approved invoices remain historical records; new approval/settlement requests require the explicit review. Synthetic demo deliveries contain clearly marked sample reviews.

Back up the whole freight database/schema together, including `freight_workspaces`, `freight_document_content`, the migration history, the format registry, and its guard function/trigger. Follow the [storage deployment and rollback procedure](storage.md). Apply database encryption, backup access, retention, and capacity policies appropriate to shipment evidence. This implementation uses PostgreSQL storage; external object-storage, automated signature verification, and document deletion/retention workflows are not configured.

Additional freight charges can bind an immutable supporting file to their proposal's original SHA-256 digest. Finance approval of that charge records its own review and counterparty confirmation; POD review remains separate. Charge approval verifies its stored bytes transactionally, and the relevant invoice issuance/approval/settlement checks those files again. Generic file rejection is blocked while an approved charge depends on it. [Charge evidence and posting locks](charges.md).

Carrier payable adjustment drafts likewise bind optional supporting files to their original digest. Posting checks that file, POD, and original charge evidence inside the tenant transaction. Settlement preparation rechecks active posted adjustment files. A posted adjustment's file cannot be rejected until the posting is reversed. Original approval and reversal confirmations remain separately readable. Canonical additional 210 events retain their original authenticated inbox evidence even when finance records a correction or dismissal.

Customer supplements also capture their optional agreement file's original digest. Issuance verifies those bytes in the same transaction as its receivable/journal/audit/receipt. A generic rejection cannot invalidate an issued non-void supplement's agreement file. Void/reconcile that invoice before rejecting its evidence. [Supplement billing](customer-supplements.md).

## Share original files with partners

Staff can publish an exact stored file to a named customer or carrier through **Shipment documents → Share file with partner**. The partner opens `/portal` and sees **Shared shipment files**. No file is automatically made available by belonging to a shipment or by being uploaded/attached as POD. Shared access remains authenticated; there is no public URL or browser-selected tenant/role.

1. Inspect the original file and filename. Select the exact customer account or carrier tender. Carrier options identify the actual carrier, tender sequence/status, and shipment reference; historical tenders can receive their own file after release. Existing legacy assignments are adopted with their retained identity and uncertain transmission history before creating a carrier grant.
2. Enter a message for the recipient and a separate private content-review note. Acknowledge that the original bytes and filename are appropriate for this recipient, then **Publish file access**. Publication checks the current load/document versions, freezes file metadata/hash and recipient/tender identity, and verifies the original stored bytes in the same transaction as its audit and receipt. Repeating the same command key replays its original result; changed requests conflict. Content review is a named staff decision; the application does not classify or redact PDF/image contents.
3. Only that counterparty sees the frozen filename, shipment reference, kind, size, hash, recipient message, current file review status, and access state. Staff review/revocation notes, financial totals, master data, and other parties' grants remain private. The partner downloads the exact immutable bytes with attachment/no-store/nosniff protections and the original SHA-256. Earlier explicitly shared files remain scoped to their original recipient/tender; they do not reveal a replacement carrier/customer's plan, price, location, or version.
4. **Partner file access** retains grants, private review notes, revocations, and download authorizations. **Revoke file access** stops future authorization under that grant and retains its original record. A new sharing decision after revocation requires the latest predecessor ID and creates a new grant; it does not reactivate the old URL. Operations, finance, and administrators can revoke access, including a mistaken financial-file disclosure. Revocation leaves the original file and all finance/POD evidence unchanged. Copies already downloaded, a carrier's own uploaded POD, and separately published rate/quote/invoice documents are independent of this grant.

Operations/finance/admin may share ordinary shipment files. A stored `carrier_invoice` or `rate_confirmation` file can be shared only with a carrier, and creation additionally requires finance/admin authority. Customer financial documents use the issued invoice/quote portal paths. The file's declared kind enforces this rule; staff must still inspect actual contents and filenames. Rejected files cannot receive new grants; rejection also holds downloads under existing grants without deleting their history. A later accepted review can restore access only under a grant that has not been revoked. Review status conveys the existing evidence decision, not automatic invoice approval or signature certification.

Publishing a file to a carrier is communication of that **exact tender**, even before a recorded download or an EDI attempt. Proven-unsent withdrawal therefore becomes unavailable. Revoking the grant cannot prove that instructions were never seen and cannot restore unsent status; obtain actual carrier release or record an actual decline. Sharing a customer's file or an old carrier tender's file does not communicate a replacement tender. File publication itself never accepts/tenders/dispatches freight, changes a commerce order, reviews POD, or posts a payment.

An open sharing form freezes the reviewed recipient identity, tender/history, original document version, and load version. Background refresh cannot silently substitute a new customer/carrier or raise its submitted version. If the shipment changes while the form is open, submission fails with a conflict and staff must reopen and review current details. This protects the actual disclosure decision as well as the stored grant.

### Authorization and revocation ordering

A partner download locks the tenant aggregate, checks the live principal and exact grant, checks original metadata/hash/bytes, records an authorization, and commits before releasing bytes. Revocation uses the same tenant lock. If revocation commits first, the download is denied; an authorization committed earlier can finish sending its already-authorized bytes. Missing/corrupt content rolls back the authorization and its audit. Records say **download authorized**; they do not establish network receipt, reading, or acceptance. No authorization is logged for a denied counterparty, rejected/revoked file, or failed integrity check.

### Sharing API and persistence

- Staff `POST /v1/documents/{document_id}/shares` under `documents.write`: `{expected_load_version, expected_document_version, audience: "customer"|"carrier", carrier_tender_id?, expected_previous_id?, message, review_note, acknowledge_content: true}`. Messages/notes require 1–200 characters. Customer identity comes from the current shipment; carrier identity comes from the selected exact tender. Omitting a carrier tender selects/adopts its current assignment. Clients cannot choose the counterparty, actor, role, content hash, file metadata, or access status.
- Staff `POST /v1/document-shares/{share_id}/revoke`: `{expected_version, note}` under `documents.write`. All business writes require `Idempotency-Key`; revocation remains available even when original bytes are corrupt.
- Partner `GET /v1/portal/files/{share_id}/content`: exact scoped bytes and a fresh live authorization; generic staff document IDs cannot be used as share IDs. Every successful authorization is audited; GET does not replay a cached business receipt or require an idempotency key.
- `GET /v1/portal` adds explicit `files` projections. Revoked/held entries retain their original descriptive metadata and access status but have no functioning download. Staff workspace responses add complete `document_shares` history, including private notes and authorizations.

Migration `013_document_sharing.sql` advances format 10 to **11**, preserving earlier records/files/history and fencing writers that could discard grants or ignore their custody effects. [Storage deployment and rollback](storage.md) covers upgrades. Qualification checks scope, forged input/role denial, financial-file rules, exact bytes, replay, private notes, revocation/resharing, rejection, legacy adoption, and historical tender isolation. PostgreSQL checks corruption rollback, competing grants, and a download racing revocation with retained authorization ordering. Browser qualification exercises the real staff and mobile partner flows. The actual EDI/Sync runtime also shares and revokes carrier-submitted POD without invalidating reviewed finance evidence.

See [API endpoints](api.md) and [role grants](access.md).

Carrier credit applications bind an optional file on their source shipment to its original digest. Application posting checks that file plus stored POD, approved original charges, and active carrier-adjustment files on the source and every target inside one tenant transaction. A corrupt target file cannot leave a partial allocation on the source. Active application evidence cannot be generically rejected until its application is reversed. Reversal remains available to unwind a mistaken allocation while retaining the original evidence and fresh carrier retraction proof. [Credit application workflow](carrier-credit-applications.md).
