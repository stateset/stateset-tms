# Restoring an interrupted save

The subsequent [native database upgrade](browser-journal-upgrades.md) prevents older journal clients from reopening upgraded storage. The subsequent [encrypted journal](sealed-save-journal.md) protects new format-2 request contents with server-held keys and converts a verified owner’s valid old entry. The plaintext format-1 storage and qualification below describe this earlier release. Unopened old entries remain subject to its local-data limits until conversion or cleanup.

The shared workspace now records an original save in this browser before sending it. Reloading, opening the shipment catalog and returning, or closing and reopening the tab can restore the same path, input and request key. Restoration sends no business operation automatically. Choose **Check original save** to retrieve or complete that original, or **Resolve original save** to keep a completed result or durably stop an unapplied original. **Original save details** shows the original target and retained values before that choice.

A completed acknowledgement is recorded before refreshing the workspace. If the refresh fails or the page reloads, **Save completed** continues to offer a read-only refresh. A stopped original remains distinct from a completed save. Neither an ordinary workspace read nor a background refresh proves the outcome of an uncertain request.

## Ownership and competing tabs

The API verifies the tenant and subject before browser recovery is opened. Journals are scoped to tenant, subject, authentication mode and organization. Clerk journals also include the Clerk session ID. Another tenant, another operator in the same tenant, or a different Clerk session cannot restore that original through the workspace. Scope identifiers do not contain credentials.

Before a shared-workspace POST, the gateway independently verifies the browser's reviewed tenant/subject using its captured upstream credential and organization. It forwards the operation with that same captured identity. A changed credential cookie therefore cannot redirect a restored body into another tenant. The expected-identity header cannot grant access; ordinary API authorization still applies, including to receipt replay. Existing routes without that header retain their prior gateway behavior.

An IndexedDB read/write transaction claims one original per owner across tabs. Two stale tabs cannot replace it with separate keys even when cross-tab notifications are unavailable. An old **Check original save** notice encountering a different current original shows that original and sends nothing; checking its different values requires another explicit choice. Successful acknowledgements and cleanup compare the original key. Checks are counted transactionally so an initial rejection cannot erase an original that another tab is already checking.

Workspace sign-out immediately closes private UI and attempts credential removal independently of local cleanup. Successful cleanup removes retained input and rotates a browser generation; late first claims and acknowledgements cannot repopulate that generation. When cleanup commits, other tabs receive an invalidation hint and close their private workspace. Without notifications, their next storage/access check still fences the old generation. If storage refuses cleanup, the credential cookie is still removed and the UI explicitly asks to retry removal of local recovery data. Clerk’s workspace sign-out similarly attempts cleanup across that session’s organizations without preventing SDK sign-out. SDK session changes also trigger cleanup; the session-specific scope independently prevents restoration into a new session. Full live Clerk sign-in/sign-out commissioning remains deployment work.

## Storage failures and retention

The journal waits for transaction completion before starting HTTP and requests strict durability. Opening storage and waiting for a transaction each have a five-second deadline. An unavailable, quota-rejected, blocked, malformed or unsupported journal pauses new saves through the shared handler. Current workspace reads remain available. **Retry recovery storage** is reachable in the workspace and an open dialog. An unreadable record is retained for recovery rather than silently discarded. Fixing the storage condition permits an explicit retry.

These transaction choices follow the [IndexedDB 3.0 Working Draft](https://www.w3.org/TR/IndexedDB/); that draft and the finite Chromium tests do not establish physical power-loss durability on every browser. Browser eviction, clearing site data, private-profile disposal, profile loss and unavailable storage can remove local recovery data. No browser journal replaces the API's durable receipts or a coordinated service backup.

The browser retains original business inputs in its origin's IndexedDB, without application-level encryption. It stores no API credential, session cookie or Clerk bearer token. Treat the browser profile as local business-data storage: the display scope is not protection against a compromised browser, local profile access or malicious same-origin code. An original has no automatic expiry that could silently discard uncertainty. A verified completed/stopped outcome followed by a successful current read removes its payload; successful workspace sign-out/access cleanup removes that scope's payload. Unreadable or blocked storage may prevent removal; a failed sign-out cleanup remains explicitly retryable. A cookie identity mismatch closes the old display while retaining its original for its own operator. Clearing local recovery does not stop a save already begun; use server resolution before sign-out when a durable stop is needed.

## Scope and evidence

The Freight backend, schema and API executable are unchanged from the format-18/migration-023 resolution release. Deploy the gateway and workspace UI together. A source reversal reconstructs the preceding code for isolated reproduction; it is not a database downgrade or an operational browser rollback procedure. The preceding UI ignores this journal, so keep a compatible UI available to resolve retained originals.

This release covers the root shared handler's nineteen save paths listed in [server resolution](save-resolution.md). Embedded quote, finance, document, partner and control-tower workflows retain independent lifecycles. Unsaved drafts and modal presentation are not restored. Original input/key restoration is separate from service-worker/offline execution, cross-device recovery and operator task-outcome evidence.
